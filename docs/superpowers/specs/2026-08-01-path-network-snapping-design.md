# 설계: 산책로 경로망 스냅 (Path Network Snapping)

- 작성일 2026-08-01 · 프로젝트 GNSSnavi
- 근거 문헌: `docs/outdoor-microscale-tracking_litreview/` (특히 `08_implications.md`)

---

## 1. 문제

야외 레이더 내비게이션에서 두 가지가 막혀 있다.

1. **인접 관 구분 불가** — 과학기술관·자연사관 입구가 20m 간격으로 마주보는데,
   진입 반경이 각 28~30m 라 두 원이 완전히 겹친다. 좌표가 완벽해도 반경 판정으로는 구분이 안 된다.
   현재 코드는 `VENUES` **배열 순서**로 결정되는 상태다(실질적 결함).
2. **위치 오차가 반경에 육박** — 실측 좌표 ±8~11m + 실시간 오차 ±12m.
   문헌상 소형 지오펜스 오탐률은 40.2% (Wray et al. 2019, `10.1111/acer.13991`).

## 2. 접근 — 측위를 개선하지 말고 갈 수 있는 곳을 제약한다

Alaoui et al. (2017, `10.1155/2017/7951346`)은 넓은 개방공간에서 A\* 라우팅 그래프로 PDR 을 보조해
**비보조 PDR 드리프트 8% → 거의 0**, **평균 오차 3–5m** 를 얻었다. 라우팅 그래프가 자이로 드리프트
보정·보폭 교정·기기 지향 어긋남 추정을 동시에 수행한다.

우리는 PDR 을 쓰지 않지만 **경로망 제약이라는 핵심 아이디어**를 가져온다.
관람객은 정해진 산책로로 다니므로, 위치를 경로 위로 끌어오면 **횡방향 오차가 산책로 폭으로 제한**된다.

**핵심 설계 판단**: 각 관 입구로 이어지는 **짧은 지선(spur)** 을 경로망에 포함시키면,
어느 지선에 스냅되는지가 곧 **어느 관으로 향하는지**가 된다.
20m 간격 문제를 거리가 아니라 **위상(topology)** 으로 푼다.

## 3. 데이터 획득 — 걸어서 기록

지도 서비스는 이 환경에서 접근이 차단되어 있고, 공식 조감도는 방위가 실제와 다르다.
따라서 **현장에서 걸으며 기록**한다.

1. `path.html` 로 산책로를 걸으며 GPS 트랙 기록 (좌표 게이트와 동일하게 **위성 락 상태에서만**)
2. Douglas–Peucker 로 단순화 → 폴리라인
3. 같은 경로를 2~3회 걸어 궤적을 합성(중앙값) → 노이즈 감소
4. `PATHS` 스니펫 출력 → `index.html` 에 붙여넣기

**이 방식의 이점**: 실측 `VENUES` 좌표와 **같은 좌표계·같은 기기**로 얻으므로 계통오차가 상쇄된다.
지도에서 디지타이징하면 지도 기준계와 GPS 기준계의 차이가 그대로 남는다.

## 4. 데이터 구조

```js
const PATHS = [
  { id:"main", name:"정문 직선로",
    pts:[[36.37550,127.37650],[36.37562,127.37668], /* ... */] },
  { id:"spur-tech", name:"과학기술관 지선", venue:"hall-tech",
    pts:[[36.37655,127.37455],[36.37669,127.37472]] },
];
```

- `pts`: `[lat, lng]` 배열. 순서가 곧 경로 방향(단, 방향 제약은 걸지 않는다)
- `venue`: 선택. 있으면 스냅 시 해당 관을 지오펜스 후보로 우선한다

## 5. 스냅 엔진 (순수 함수)

```
snapToPaths(fix, acc) → { lat, lng, pathId, venue, dist } | null
```

1. 모든 폴리라인의 모든 세그먼트에 대해 **점–선분 최단거리**와 그 수선의 발을 구한다
   (수선의 발이 선분 밖이면 가까운 **끝점**을 쓴다)
2. 최소 거리 세그먼트를 선택
3. **신뢰 조건**: 스냅 허용 거리는 **결합 불확실성**으로 정한다.
   경로망 자체도 GPS 로 기록해 오차를 안고 있으므로 현재 정확도만으로 판단하면 안 된다.
   ```
   tol  = min(K_TOL * hypot(acc, PATH_ERR), SNAP_MAX)
   dist > tol  →  null (스냅 포기)
   ```
4. **가중 이동**: 완전 스냅이 아니라 보간한다.
   ```
   w      = clamp(acc / (acc + PATH_ERR), 0, MAX_W)
   result = fix + w * (snapPoint - fix)     // w=0 원위치, w=1 완전 스냅
   ```
   정확도가 나쁠수록 `w` 가 커져 경로를 더 신뢰하고, 좋을수록 원위치를 신뢰한다.

**파라미터 초안** (현장 검증 후 조정)

| 이름 | 초안값 | 의미 |
|---|---|---|
| `PATH_ERR` | 8m | 기록된 경로망 자체의 가정 오차 (다중 통과 합성 후) |
| `K_TOL` | 1.5 | 결합 불확실성의 몇 배까지 "경로 위"로 인정할지 |
| `SNAP_MAX` | 25m | 절대 상한. 아무리 부정확해도 이보다 멀면 스냅하지 않음 |
| `MAX_W` | 0.8 | 완전 스냅(1.0)을 허용하지 않아 오매칭 피해를 제한 |

예: `acc=8` → `tol = 1.5 × hypot(8,8) = 17m`, `w = 8/16 = 0.5` (절반만 끌어옴)
`acc=25` → `tol = min(1.5×26, 25) = 25m`, `w = 25/33 = 0.76` (강하게 끌어옴)

## 6. 지오펜스 통합

현재 판정에 **후보 좁히기** 단계를 추가한다.

```
1. 스냅 결과에 venue 가 있으면 → 그 관을 우선 후보로
2. 후보가 여전히 복수면 → 진행방향과 가장 잘 맞는 관
3. 진행방향이 없으면 → 가장 가까운 관 (nearest)
4. 그 다음 기존의 정확도 적응형 반경·dwell 판정
```

이로써 **배열 순서로 결정되던 결함**이 함께 제거된다.

## 7. 실패 모드 방어 (Berjisian & Bigazzi 2022, `10.1049/itr2.12250`)

문헌이 보고한 보행 맵매칭 실패 원인과 대응:

| 실패 모드 | 대응 |
|---|---|
| 평행 시설 (나란한 두 길) | **주요 동선만** 등록. 촘촘한 경로망을 만들지 않는다 |
| 누락 링크 (등록 안 된 실제 통행로) | `SNAP_MAX` 상한 → 멀면 스냅 포기하고 원위치 유지 |
| 역방향 통행 | 방향 제약을 걸지 않는다 (산책로는 양방향) |
| 외부 검증 시 성능 저하 | 스냅 전/후를 화면에 동시 표시하는 **검증 토글** 제공 |

## 8. 오류 처리

- `PATHS` 가 비어 있으면 **스냅 비활성** → 기존 동작 그대로 (안전한 기본값)
- 폴리라인 점이 2개 미만이면 해당 경로 무시
- 스냅 실패는 조용히 넘어간다 (사용자에게 노출할 오류가 아님)
- 스냅은 **표시·판정에만** 쓰고, `collect.html` 의 좌표 수집에는 절대 적용하지 않는다
  (측정값에 보정을 섞으면 실측의 의미가 사라진다)

## 9. 테스트

**단위 (스냅 엔진 — 순수 함수라 브라우저 불필요)**
- 알려진 직선 폴리라인 + 수직으로 d미터 떨어진 점 → 스냅 거리 d, 수선의 발 좌표 일치
- 선분 끝점 너머의 점 → 끝점으로 스냅 (수선의 발이 선분 밖일 때)
- `dist > SNAP_MAX` → `null`
- 지선 두 개 사이 위치 → 가까운 쪽 `venue` 반환

**통합 (브라우저)**
- `PATHS` 비었을 때 기존 동작 유지 (회귀)
- 스냅 활성 시 마커·배경이 일관되게 이동
- 인접 두 관 사이에서 지선 스냅으로 올바른 관 판별

**회귀**: 기존 `test/collect-gate.test.js`(8항목), `test/geofence-adaptive.test.js`(7항목)

## 11. 범위 밖 (명시적 제외)

- PDR/추측항법 — 경로망이 같은 문제를 더 싸게 해결하므로 후순위로 강등
- 인프라 기반 측위(UWB·BLE·RTK 기준국)
- 자동 경로망 생성 — 수동 기록으로 충분한 규모
- 종방향(경로 진행 방향) 오차 개선 — 이 설계는 **횡방향만** 다룬다

## 12. 알려진 한계

- 문헌의 맵매칭 성능(70–90%)은 **도시 교통망** 기준이다.
  **과학관 산책로 규모에 경로망 제약을 적용한 선행연구를 찾지 못했다**(연구 공백).
  따라서 이 적용은 직접 이식이 아니라 **규모 이전(transfer)** 이며, Berjisian 이 경고한
  "전이성 부족"이 그대로 적용된다. **현장 검증 없이 성능을 주장하지 않는다.**
- 관람객이 잔디·비공식 동선으로 다니면 스냅이 오히려 방해가 된다. `SNAP_MAX` 로 제한하지만
  완전히 막지는 못한다.
- 경로 기록 자체가 GPS 기반이라 **경로망도 ±수 m 오차를 안고 있다.**
  다중 통과 합성으로 줄이지만 0 이 되지는 않는다.

## 12-1. 현장 실측으로 확정된 기하 (2026-08-03)

설계 당시 "겹치는 쌍"은 **더미 좌표와 ±22m 값을 뺀 숫자**였다. 현장 실측으로 바로잡는다.

**7개 관 전부 실측 완료 (2026-08-03).** 21개 쌍 중 반경이 겹치는 것은 **하나뿐**이다.

| 쌍 | 거리 | 판정 |
|---|---|---|
| 과학기술관 ↔ **자연사관** | **15.6m** | ⚠ 완전 중첩 (진입반경 합 52m) |
| 그 외 20개 쌍 중 최근접 (미래기술관 ↔ 천체관) | 85.5m | 분리 (여유 충분) |

| 관 | 정확도 | 산포 | 채택 |
|---|---|---|---|
| 생물탐구관 | ±6m | 0.4m | 31/31 |
| 과학기술관 | ±6m | 0.7m | 35 (diag 로그) |
| 자연사관 | ±7m | 0.5m | 37 (diag 로그) |
| 미래기술관 | ±7m | 1.1m | 31/31 |
| 어린이과학관 | ±8m | 0.8m | 28/31 |
| 창의나래관 | ±8m | 0.6m | 28/34 |
| 천체관 | ±10m | 2.0m | 23/31 (벽면 다중경로 의심) |

부지 외접 범위는 남북 284m × 동서 250m.

- **중첩 쌍은 하나뿐**이고, 처음 지적하신 대로 **과학기술관 ↔ 자연사관**(볼트러스 아치 아래
  마주보는 두 입구)이다. 설계 §1 이 근거로 삼은 `hall-tech ↔ hall-future` 14.1m 은 허수였다.
  **제약이 필요하다는 전제 자체는 실측으로 더 강해졌다** — ±6~7m 의 좋은 좌표로도
  반경 판정으로는 절대 구분되지 않는다.
- 측정 품질: 과학기술관 ±6m(채택 35, 산포 0.7m) · 자연사관 ±7m(채택 37, 산포 0.5m) ·
  미래기술관 ±7m(양호 31/31, 산포 1.1m). 세 측정 모두 고도가 49~50m 로 수렴해 교차 검증된다.
- **락까지 약 25초 걸린다.** 락 전에 수집을 시작하면 30초 창의 앞부분이 통째로 버려진다
  (어린이과학관의 `양호 5/32` 가 정확히 그 현상). 정확도가 10 이하로 떨어진 뒤 시작할 것.
- 볼트러스 아래는 **±14~22m 에서 더 좋아지지 않는다.** 위치는 정지해 있는데 정확도만 나쁜
  — 산포가 아니라 위성 기하가 나쁜 상태다. 고도가 46~49m 로 개활지와 같은 대역이라
  WiFi 폴백이 아니라 **열화된 위성해**다. `collect.html` 이 좌표를 거부하는 게 정상 동작.

## 13. 현장에서 먼저 확인할 것 (구현 후 추가)

구현·리뷰 과정에서 드러났지만 **시뮬레이션으로는 재현할 수 없어** 현장 관측이 필요한 항목들이다.

- **두 관 사이에서 걸을 때의 전환 빈도.** 판별에 진 관의 진입 상태를 풀어 주도록 고쳤기 때문에
  화면 전환이 다시 가능해졌지만, 그 대가로 걷는 관람객이 **최대 `T`(3초)마다 전환**될 수 있다.
  정지 상태에서는 진행방향이 6m 이동 전까지 갱신되지 않아 판정이 고정되므로 문제가 없다.
  GPS 가 두 관 사이를 튀는 상황은 시뮬레이터로 만들 수 없으니 **현장에서 가장 먼저 볼 것.**
- **간선이 지선보다 문에 가까운 경우.** 스냅은 모든 경로를 통틀어 최근접 세그먼트를 고르므로,
  기록한 간선이 어느 관 문에 지선보다 가까이 지나가면 `venue` 가 `null` 로 나오고
  **위상 판별이 조용히 꺼진다.** 지선을 문 쪽으로 충분히 붙여 기록하고, 의심되면
  `🛤 경로스냅` 토글로 전/후를 비교한다. (현재 토글은 스냅 여부만 보여주고 어느 경로에
  붙었는지는 표시하지 않는다 — 오스냅이 눈에 잘 띄지 않는다는 뜻이다.)
- **`PATHS` 는 손으로 붙여넣는 데이터다.** 좌표가 하나라도 망가지면 스냅을 포기하도록
  방어해 두었지만(`Number.isFinite` 검사), 붙여넣은 뒤에는 반드시 앱을 열어
  마커가 정상으로 뜨는지 눈으로 확인한다.
- **판정 우선순위 ③(최근접)은 사실상 도달하지 않는다.** 진행방향이 한 번 잡히면 초기화되지
  않아 ②에서 결정된다. 현장에서 ②의 판정이 미덥지 않으면 그때 조정 대상이다.
