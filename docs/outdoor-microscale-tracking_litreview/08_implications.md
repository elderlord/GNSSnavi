# GNSSnavi 적용 함의

문헌조사(`07_review.md`)를 우리 프로젝트의 실제 결정으로 옮긴 것.

---

## 1. 우리가 이미 한 선택은 문헌과 맞다 (근거가 생겼다)

| 우리 결정 | 문헌 근거 |
|---|---|
| 정확도 적응형 지오펜스 (부정확하면 자동전환 포기 → 수동 버튼) | 소형 지오펜스는 신뢰도가 낮고[D1], 오탐률이 높다[D3]. 추적 프로파일·dwell 조정이 표준 완화책[D1][D4] |
| 3초 dwell 유지 | dwell 임계는 문헌·업계가 공통으로 권하는 오탐 억제 수단 |
| 좌표 품질 게이트(±12m) | 기기 간 편차가 커 "주파수 수로 일반화 불가"[A4] → 기기·장소별 실측 검증이 정답 |
| 나침반 대신 GPS 진행방향 | 자력계는 국소 자기간섭에 취약[C5]. 금속 트러스 아래에서 특히 |
| 레이더(방향+거리) UI | 정밀 측위를 전제한 관람 안내는 반복 실패[E1][E4][E5]. 방향·거리는 정밀도 의존이 낮다 |

**결론**: 지금까지의 보수적 선택은 문헌이 지지한다. 되돌릴 이유가 없다.

## 2. 가장 큰 미개척 지렛대 — 경로망 스냅 (맵매칭)

sidewalk matching[B1]이 **단순 보행로 지도만으로 18m → 5m** 를 만들었다. 우리 조건은
그 논문(홍콩 도심 협곡)보다 **유리하다**:

- 부지 보행로가 단순하고 **개수가 적다** (도심 도로망 대비)
- 관람객은 대부분 **정해진 산책로**를 걷는다 (자유 보행이 아님)
- 우리는 이미 **부지 좌표계와 배경 도식**을 갖고 있다

다만 문헌 기법을 그대로 못 쓴다. sidewalk matching 은 **위성 방위각·C/N0 원시 관측치**를 쓰는데
**브라우저에서는 접근 불가**다. 우리가 쓸 수 있는 건 **경로망 제약 부분만**이다:

> 주요 산책로를 폴리라인으로 정의하고, 위치를 가장 가까운 경로 위로 스냅한다.
> 경로에 수직인 방향(횡오차)이 크게 줄어들고, 경로를 따르는 방향(종오차)만 남는다.

**예상 효과**: 산책로 폭이 좁을수록 횡오차가 그 폭으로 제한된다. 정문 직선 구간처럼
길이 하나뿐인 곳에서는 2차원 오차가 사실상 1차원으로 줄어든다.
**비용**: 산책로 폴리라인 데이터(현장 답사 또는 항공사진에서 디지타이징) 한 번.

## 3. PDR 은 "터널 브리징"으로만 한정하면 타당하다

문헌은 PDR 이 **단거리에서 강하고**(수평오차 1.6m 미만[C1]) **장거리에서 드리프트로 무너진다**[C5]고
일관되게 말한다. 우리 용도는 **짧은 아치 터널 통과 구간**이므로 문헌이 말하는 강점 구간에 정확히 들어간다.

단, 문헌이 지적한 자기간섭 문제[C5]가 우리 터널(금속 트러스)에 그대로 적용된다.
→ **방향을 나침반에서 얻지 말고, 터널 진입 직전의 GPS 진행방향으로 고정**하는 접근이 맞다.
(직선 터널이라면 통과 중 방향이 거의 변하지 않으므로 이 근사가 성립한다.)

**주의**: 이건 부가 기능이지 핵심이 아니다. 터널이 짧다면 그냥 "터널 안에서는 판정 보류"로
두는 편이 코드 복잡도 대비 낫다.

## 4. 인접 두 관 구분 — 우리 아이디어가 문헌 계열과 맞닿아 있다

sidewalk matching 이 푸는 문제가 **"도로의 어느 쪽에 있는가"** 인데, 이는 우리의
**"마주보는 두 문 중 어느 쪽인가"** 와 구조가 같다. 둘 다 **위치를 더 정확히 아는 대신,
가능한 선택지를 좁혀 판별하는** 접근이다.

문헌은 위성 가시성으로 판별했지만(브라우저 불가), 우리는 **진행방향**으로 판별할 수 있다.
앞서 계산한 대로 마주보는 문(180° 차이)은 20m 접근 시 99.6% 로 구분된다.
**문헌의 문제의식과 같은 계열이되, 브라우저에서 가능한 수단으로 치환한 것**이다.

## 5. 기대치 조정 — 문헌이 말해주는 현실

- **1m 는 인프라 없이 불가능.** 최선의 보고치가 이중주파수 2m, 융합 1.6m 대다[A1][C3].
  그것도 개활지·정적 조건이다.
- **반경 20~30m 지오펜스는 문헌이 "어렵다"고 보는 영역.** 우리가 겪은 문제는
  구현 실패가 아니라 **원래 어려운 문제**였다.
- **정밀 측위에 기댄 관람 안내는 반복 실패했다**[E1]. 우리 레이더 UI 처럼 **정밀도 의존이 낮은
  설계**가 오히려 문헌의 교훈에 부합한다.

## 6. 권고 — 우선순위

| 순위 | 조치 | 근거 | 비용 |
|---|---|---|---|
| **1** | **주요 산책로 경로망 스냅** 도입 | [B1] 인프라 없이 최대 개선 | 폴리라인 데이터 1회 + 스냅 로직 |
| **2** | **진행방향 기반 인접 관 판별** | 자체 계산 99.6%, [B1] 과 같은 계열 | 접근방향 장기 baseline 유지 |
| 3 | 지오펜스 신뢰도 사전 추정 지표 도입 검토 | [D2] | 원문 확인 필요 |
| 4 | 터널 PDR 브리징 | [C1] 단거리 강점 | 복잡도 높음, 후순위 |
| — | ~~RTK/UWB/BLE~~ | 인프라 전제 → 범위 밖 | — |

**핵심 메시지**: 측위를 더 잘하려는 노력(PDR·필터링)보다, **갈 수 있는 곳을 제약으로 넣는 것**
(경로망 스냅)과 **선택지를 좁혀 판별하는 것**(진행방향)이 우리 조건에서 훨씬 유리하다.
이것이 문헌이 반복해서 말하는 교훈이다.
